# mac-toolkit 設計方針

このドキュメントは実装の判断基準です。迷ったらここに立ち返り、方針を変えるときはこのファイルを先に更新します。

## 1. このアプリが目指すもの

Stats・Shottr・その他の常駐ユーティリティを 1 つにまとめた macOS メニューバーアプリ。
バラバラの常駐アプリを何本も動かす代わりに、**1 プロセス・1 タイマー**で全部を賄うことを最大の価値とします。

そのため次の順で優先します。

1. **省電力** — 常時動くアプリなので、無駄なウェイクアップを作らない
2. **落ちない・壊れない** — 低レベル API は機種依存で失敗する。失敗しても他の機能を巻き込まない
3. **機能の豊富さ**

「Stats にあるから」ではなく「1 つにまとまっていて嬉しいか」で機能を判断します。

## 2. 技術スタック

| 項目 | 選択 | 理由 |
|---|---|---|
| 言語 / UI | Swift 6 + SwiftUI `MenuBarExtra` | IOKit・CoreWLAN・ScreenCaptureKit に直接触れる。常駐アプリのフットプリントが小さい |
| ビルド | SwiftPM のみ | Xcode 不要。`swift build` が通ることを常に維持する |
| 配布 | `scripts/bundle.sh` で `.app` を生成 + ad-hoc 署名 | `LSUIElement` とバンドル ID を効かせるためにバンドル化が必須 |
| 最低 OS | macOS 14 | `MenuBarExtra`・`@Observable`・`SMAppService` が揃う最初の安定版 |
| 依存ライブラリ | 原則ゼロ | 全て OS 標準 API で実現できる。依存を足すときは Issue で理由を明示する |

並行性は Swift 6 の strict concurrency を有効なまま維持します。**ビルド警告ゼロを常時保つ**（警告を残すと本当に危ない警告が埋もれるため）。

## 3. 中核となる抽象: ToolModule

全機能は `Sources/MacToolkit/Core/ToolModule.swift` の `ToolModule` に準拠した 1 クラスとして実装します。機能ごとに独自の常駐処理や Timer を持たせません。

```
ToolModule (@MainActor, AnyObject)
├─ id / title / systemImage     … 識別と表示
├─ isAvailable                  … この Mac で使えるか（例: デスクトップ機ならバッテリーは false）
├─ start() / stop()             … 有効化・無効化のライフサイクル
├─ tick()                       … Sampler から毎周期呼ばれる。ここで値を更新
├─ statusItemView()             … メニューバー本体の小さな表示（不要なら nil）
├─ detailView()                 … ポップオーバー内の詳細
└─ settingsView()               … 設定画面のこのモジュール固有の項目（不要なら nil）
```

### 決めごと

- **モジュールは MainActor 上で動く。** UI から直接読まれるため。重い処理（OCR、スクリーンショット合成など）だけを個別に `Task.detached` へ逃がします。
  例外は `ScreenRecorder` で、`SCStream` が毎秒 30 回サンプルを返すため専用のシリアルキューを持ちます。
  ただし `RecordingModule` 自体は MainActor のままで、キューに触れるのは `ScreenRecorder` の内側だけです。
  これは「値の取得を担う型」を UI 非依存に切り出す既存の形（`*Counters` / `*Sensors`）の延長で、
  モジュール本体が並行性を抱え込まないという線は守っています。
- **View は `AnyView` で型消去する。** `associatedtype` にすると `ModuleRegistry` が異種のモジュールを 1 つの配列で保持できなくなるため、意図的に型消去を選んでいます。
- **モジュール同士は互いを参照しない。** 依存が必要になったら `ModuleRegistry` 経由か、共有の値型を `Core/` に置きます。
- **`tick()` は必ず軽い処理にする。** 目安 1ms 未満。重い取得は自前でキャッシュし、数周期に 1 回だけ実際に取りに行く。

### 新しいモジュールの追加手順

1. `Sources/MacToolkit/Modules/<機能名>/` にクラスを作る
2. `MacToolkitApp.init` の登録配列に 1 行足す
3. 以上（登録順がメニューバーの表示順になります）

## 4. サンプリングと省電力

`Core/Sampler.swift` が**アプリ全体で唯一のタイマー**です。毎周期、有効なモジュールの `tick()` を順に呼びます。

- モジュール個別に `Timer` / `DispatchSourceTimer` を作ることを禁止します
- タイマーは `.common` ランループモードで登録（メニュー操作中も更新を止めないため）
- `tolerance` を間隔の 10% に設定し、OS にウェイクアップをまとめさせる
- 更新間隔は設定画面から変更でき、既定は 1 秒

イベント駆動で取れる情報（Wi-Fi の接続変化、電源の抜き差しなど）は**ポーリングせず OS の通知を使う**こと。ポーリングは「連続的に変化する数値」（速度・使用率・温度）だけに使います。

例外: **クリップボードの変更検知**（`NSPasteboard.changeCount`）だけは、連続的な数値ではないのにポーリングします。macOS に pasteboard 変更の公開通知が存在せず、これが唯一の公開手段のためです。この場合も独自 Timer は作らず `Sampler` の `tick()` に相乗りします。詳細は [docs/CLIPBOARD.md](CLIPBOARD.md) を参照。

将来的な省電力の余地として、ポップオーバーを閉じている間は詳細情報の更新を止める（メニューバーに出す値だけ更新する）ことを検討します。ただし基盤が固まるまでは複雑さを避けて実装しません。

## 5. 状態管理と永続化

- `ModuleRegistry` が `@Observable` で唯一の真実の情報源。SwiftUI は全てここを見ます
- 有効なモジュールの id 集合と更新間隔は `UserDefaults` に保存
- 初回起動時は、利用可能なモジュールを全て有効にする
- モジュール固有の設定は `<module.id>.<キー名>` という名前空間で `UserDefaults` に保存し、キーの衝突を防ぐ

## 6. 失敗の扱い（重要）

IOKit / SMC / GPU 統計は**機種・OS バージョンによって普通に取得できません**。以下を鉄則とします。

- **取得失敗でクラッシュさせない。** 強制アンラップ（`!`）と `try!` を低レベル API 周りで使わない
- **取れない値は「N/A」と表示する。** 0 と表示すると「正常に 0」と誤読される
- **キー名はフォールバック候補のリストで持つ。** 例: GPU 使用率は `Device Utilization %` → `GPU Activity(%)` の順に探す
- **`isAvailable` が false のモジュールは登録段階で除外する。** 使えない機能を設定画面に並べない
- **Mach / IOKit の資源は必ず解放する。** `vm_deallocate`、`IOObjectRelease` の呼び忘れは常駐アプリでは致命的なリークになる
- 動作確認は必ず**標準ツールと突き合わせる**（アクティビティモニタ、`powermetrics`、Finder の空き容量など）

## 7. 権限の扱い

| 機能 | 必要な権限 |
|---|---|
| Wi-Fi の SSID | 位置情報 |
| スクリーンショット | 画面収録 |
| ホットキー | 不要（Carbon の `RegisterEventHotKey` を使うため。`Core/HotKeyCenter.swift`） |
| クリップボード履歴の自動貼り付け | アクセシビリティ（既定オフのオプトイン） |
| RDP 入力の英数・かな切り替え | 不要（CGEventTap ではなく、対象アプリが前面の間だけ `RegisterEventHotKey` で英数・かなを横取りする。前面アプリの変化は `NSWorkspace` の通知で拾う） |

- **権限は「その機能を初めて使うとき」に要求する。** 起動直後にまとめて要求しない
- 未許可でも**アプリ全体は正常に動く**こと。該当モジュールだけが「権限が必要です」と表示し、システム設定を開くボタンを出す
- 権限が絡む機能は `swift run` ではなく `.app` で検証する（未署名・非バンドルだと権限の付与が安定しないため）

## 8. UI

- メニューバー本体は**幅が揺れないこと**を最優先。数値は必ず `.monospacedDigit()`、単位を含めた桁数を固定する
- `MenuBarExtra` は `.menuBarExtraStyle(.window)`。将来グラフを載せるため
- ポップオーバーはモジュールを縦に並べるだけ。1 モジュール 1 セクション
### 言語は日本語（確定方針）

**ユーザーに見える文字列は全て日本語で書く。** 英語版は作りません。

対象は「画面に出るもの全て」です。

- メニューバー・ポップオーバー・設定画面のラベル
- エラーメッセージ、権限の要求理由（`Info.plist` の `NS*UsageDescription`）
- 通知、メニュー項目、ツールチップ、空状態の文言

具体的な決めごと:

| 種類 | 方針 | 例 |
|---|---|---|
| モジュール名 | 日本語 | 「ネットワーク」「メモリ」「バッテリー」 |
| 定着した技術用語 | 英字のまま | CPU / GPU / Wi-Fi / SSID / RSSI / IP / OCR |
| 単位・数値 | 英字記号のまま | `MB/s`、`GHz`、`dBm`、`42%`、`58°C` |
| 項目名 | 日本語 | 「使用率」「空き容量」「信号強度」「サイクル数」 |
| 状態 | 日本語 | 「充電中」「取得できません」「権限が必要です」 |

無理に訳さないこと。「中央処理装置」「無線 LAN」のような直訳はかえって読みにくいので、定着している英字表記はそのまま使います。判断に迷ったら**アクティビティモニタとシステム設定の日本語表記に合わせます**（macOS ユーザーが既に見慣れている語彙のため）。

文体は常体・体言止めを基本とし、句点は付けません（「取得できません」であって「取得できません。」ではない）。ボタンは「設定…」「終了」のように macOS の慣習に従います。

### 実装上の扱い

- 文字列は**ソースに日本語リテラルを直接書く**。`Localizable.strings` は作りません
- ただし `Text("使用率")` のように SwiftUI の `Text` / `Label` に直接渡す形を保つこと。将来ローカライズが必要になったら、これらは `String(localized:)` へ機械的に置換できます
- **コード内の識別子・コメント・ログは対象外。** 変数名・型名・`id` 文字列は英語、`NSLog` の出力も英語のまま（開発者向けであってユーザー向けではないため）
- README と Issue も日本語で書く

## 9. 実装の順序

1. ~~基盤（`ToolModule` / `ModuleRegistry` / `Sampler`）~~ ✅ 完了
2. **ネットワーク速度**（Issue #2）— 初の実モジュール。`tick()` での差分計算という最も基本的なパターンをここで確立する
3. **CPU**（#4）→ **メモリ**（#7）— Mach API のパターンを確立
4. **Wi-Fi**（#3）— イベント駆動と権限リクエストのパターンを確立
5. **設定画面の本格化**（#10）— モジュールが 4 つ揃った時点で必要になる
6. **GPU**（#5）→ **温度・ファン**（#6）→ **ディスク・バッテリー**（#8）— 機種依存が最も強く、実機検証が要る
7. **スクリーンショット**（#9）— 他と性質が全く違い規模も大きいので最後。段階的に進める
8. **画面録画** — スクリーンショットの ScreenCaptureKit を再利用。会議相手の声を録るためシステム音声を含める

各段階で「パターンを 1 つ確立してから次へ」進めます。似た機能をまとめて実装しません。

`PlaceholderModule` は実モジュールが 2 つ揃った時点で削除します。
